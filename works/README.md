# Replicable computational procedures of this work

This folder contains the computational procedures used in this project, 
together with the data elements used or produced during these procedures. 
It includes reusable code modules, step-level pipeline scripts, the intermediate-data folder, 
the packaged visualisation-data folder, folders for generated figures and tables, the log folder, 
and the temporary folder.

The organisation of this folder is designed to make the computational procedures partially reproducible. 
Users do not need to rerun the entire project from the beginning if they only wish to inspect, replicate, or extend 
a specific stage of the analysis. 
The workflow is divided into ordered step-level pipeline scripts, 
while execution logs, intermediate data, visualisation data, and generated figures/tables are stored in dedicated folders.

## Library structure

The `works` folder contains the following subfolders and scripts.

| name        | type     | purpose                                                                                                                      |
|-------------|----------|------------------------------------------------------------------------------------------------------------------------------|
| `exp`       | folder   | store experimental data or experiment-related files used by the computational procedures.                                    |
| `fig`       | folder   | store generated figures produced by the visualization scripts.                                                               |  
| `log`       | folder   | store runtime logs and execution records generated during workflow execution.                                                |  
| `pkg`       | folder   | store the packaged data files used for visualisation.                                                                        | 
| `raw`       | folder   | store intermediate raw data generated or reused by the computational procedures.                                             |   
| `tab`       | folder   | store generated tables and tabular outputs produced by the visualization scripts.                                            |
| `tmp`       | folder   | store process data like files generated by clustering and alignment software.                                                | 
| `__init__`  | module   | centralise commonly used imports from the reusable code modules and defines shared path variables for the different folders. |   
| `code_*.py` | module   | provide reusable functions for specific computational tasks.                                                                 | 
| `step_*.py` | pipeline | provide ordered workflow entry points for reproducing the main analyses, packaging data, and generating figures/tables.      |  
| `README.md` | document | describe the computational procedures and their replicability.                                                               |   


### Reusable code modules

The `code_*.py` files contain reusable computational components. 
These files are intended to define core functions, algorithms, and helper procedures 
that are called by the step-level pipeline scripts.

| name                 | role(s)                                                                                                                                                                    |
|----------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `code_comparable.py` | provide functions and procedures for comparable analyses and benchmark-oriented comparisons, specifically those related to the Composite HEDGES Nanopore pipeline.         |
| `code_converting.py` | provide functions and procedures for comparative analyses involving DNA Fountain and HEDGES, as well as upstream conversion procedures used by SPIDER-WEB.                 |
| `code_correcting.py` | provide functions and procedures for introducing random sequence errors, performing A-star search (as part of HEDGES), and implementing callable outer codes.              |
| `code_estimating.py` | provide fitted formulas and estimation procedures for evaluating SPIDER-WEB-related performance metrics.                                                                   |
| `code_retrieving.py` | provide functions and procedures for pre-synthesis sequence design in SPIDER-WEB, together with data structures and operations used for sequence ranking during retrieval. |

### Step-level pipeline scripts

The `step_*.py` files are the main entry points for reproducing the computational procedures. 
They are organised according to the logical order of the project workflow.

| name                        | role(s)                                                                                                                                            |
|-----------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------|
| `step_1_preparation.py`     | create the high-compatibility coding digraph for SPIDER-WEB and constructs coding digraphs under different design constraints.                     |
| `step_2_simulations.py`     | run the major coding, correcting, and retrieving simulation analyses reported in the Main Text and Supplementary Information.                      |
| `step_3_experiments.py`     | run the experimental-design procedures and the analyses of the major experimental results reported in the Main Text and Supplementary Information. |
| `step_4_supplements.py`     | run supporting analyses related to the simulation and experimental results reported in the Main Text and Supplementary Information.                |
| `step_5_packaging.1.py`     | package the visualization data associated with the figures included in the Main Text.                                                              |
| `step_5_packaging.2.py`     | package the visualization data associated with the figures and tables included in the Supplementary Information.                                   |
| `step_6_visualization.1.py` | generate the figures included in the Main Text using the packaged visualization data.                                                              |
| `step_6_visualization.2.py` | generate the figures and tables included in the Supplementary Information using the packaged visualization data.                                   |

## Recommendations before running the replicability workflow

### Obtain controlled-access materials from the authors

Typically, the controlled-access material required for independent third-party reproduction is the C++ implementation 
of the SPIDER-WEB retrieval process, named `accelerator`.
This module is not distributed directly through the public repository. 
Users who intend to replicate pipelines that depend on the C++ retrieval implementation 
should contact the [authors](https://github.com/BGI-SynBio/SPIDER-WEB/blob/main/CORRESPONDENCE.md) 
to obtain access and agree on the corresponding usage period.

### Select and install dependencies for the intended replicability scope

Before running the workflow, users should first decide which part of the project 
they intend to replicate and install the corresponding dependencies. 
The full workflow may require a broader set of Python packages and external command-line tools.
For detailed environment information, please refer to the 
[`envs`](https://github.com/BGI-SynBio/SPIDER-WEB/tree/main/envs) folder. 
For most replicability-oriented use cases, 
we recommend installing the replicability-oriented Conda environment defined in 
[`spiderweb-repl.yml`](https://github.com/BGI-SynBio/SPIDER-WEB/blob/main/envs/spiderweb-repl.yml).

### Download, place, and verify experimental data

If users intend to replicate the results related to Fig. 3, Fig. 4, and Fig. 6, 
or other wet-lab experiment-related analyses reported in the corresponding publication, 
they should download the experimental data required for their intended replicability scope and 
place the files under the corresponding subfolders in the local `exp` folder.

After downloading, users should preserve the original folder structure and file names 
unless the corresponding paths are manually updated in the pipeline scripts. 
Users are also recommended to verify file integrity using the MD5 checksums and file-size information 
provided in the `README.md` files of the corresponding experimental-data folders.

## Recommendations while running the replicability workflow

The pipelines in `step_*.py` can generally be divided into four categories according to their computational roles. 
These categories provide a practical way to understand what each pipeline is expected to 
generate, organise, analyse, or visualise during the replicability workflow.

| pipeline category                 | main role                                                                                                                               | main replicability value                                                      | recommended handling                                                                                                                   |
|-----------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| data-element generation pipelines | generate data elements required by downstream pipelines, including algorithmic hyperparameters, coding digraphs, and sequence datasets. | verify that the required data elements are generated as expected.             | check output files, formats, and downstream compatibility; rerun only when upstream generation needs to be inspected or modified.      |
| data-organisation pipelines       | organise or transform existing data, including random sampling of experimental data and extraction of visualisation data from raw data. | verify that existing data are correctly sampled, transformed, or packaged.    | check whether the organised outputs match the expected structure and can be consumed by downstream pipelines.                          |
| analysis pipelines                | run procedures to obtain simulation or experimental results.                                                                            | replicate the simulation or experimental results reported in the publication. | treat these as the primary replication targets; account for possible dependence on hardware, software versions, and random procedures. |
| visualisation pipelines           | generate figures or tables from packaged visualisation data.                                                                            | verify the mapping from data elements to publication-ready figures or tables. | use these to regenerate figures and tables and to identify reusable visualisation assets.                                              |

In practice, data-element generation and data-organisation pipelines may not always need to be rerun 
when their expected outputs are already provided and can be directly verified. 
Analysis pipelines are usually the primary focus of replication 
because they produce the reported simulation or experimental results. 
Visualisation pipelines are mainly useful for checking 
how packaged visualisation data are converted into figures and tables, 
and for identifying visualisation data or plotting procedures that may be reused in other projects.

"source–process–target" structure.

Specifically, `source` denotes the data element consumed by a pipeline; 
`external` uses an asterisk (`*`) to indicate that the corresponding `source` is an external data element 
rather than an output generated by another pipeline in this repository; 
`process` denotes the software component that performs the corresponding operation; 
`target` denotes the data element produced by that operation; 
and `terminal` uses an asterisk (`*`) to indicate that the corresponding `target` can serve as a terminal output 
of the replicability workflow.
